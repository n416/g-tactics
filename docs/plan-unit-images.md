# 計画: ユニット画像の全面作り直し

作成: 2026-07-16 / 状態: **計画確定・未着手**

## 背景と現状

- 現行のユニット画像は他サイトから収集したもので、品質・スタイルがバラバラ。権利面でも全作り直しが前提。
- DBユニット数: **911**(image 参照 910 件)
- 実ファイル: **585枚**(`frontend/public/images/units/`、ほぼGIF、幅75〜130px、セル塗り全身・左向き・透過)
- **325件はファイル欠落**(元サイトにも無かった)。現状はプレースホルダ表示。
- 表示は `frontend/src/components/UnitImage.tsx` に集約済み。`VITE_UNIT_IMAGE_BASE` で配信元差し替え可。

## 基本方針

**リドロー方式**: 既存画像(または収集した設定画)を参照画像として ChatGPT に渡し、
「この画像のメカをデザインそのまま、指定スタイルで描き直し、透過背景で出力」させる。

- 理由1: 910機の大半はマイナー機体で、テキストだけでは正しい姿が出ない。参照画像が唯一の担保。
- 理由2: 機体名を書かずに済むため、版権名による生成拒否を回避しやすい。
- ChatGPT 操作は `~/.claude/skills/chatgpt-imagegen/` スキルで自動化(ログイン済みChrome)。

**プランB**: ローカル NVIDIA GPU あり(確認済み)。ChatGPT の品質が不合格なら
SD(ComfyUI or A1111)+ アニメ系 checkpoint + ControlNet(lineart/tile)+ img2img バッチに切り替え。
スタイル固定・全量一晩処理が利点、デザイン忠実度と透過品質が課題。

**欠落325件**: 設定画のWeb収集を **agy に委譲**(`agy-delegation` スキル参照)。
収集できた分から同じリドローパイプラインに合流。収集不能な機体はプレースホルダ継続。

## 確定スタイル(フェーズ0で決定: C案「設定資料画風」)

発注プロンプト(1行で入力すること。改行は送信になる):

> 添付はゲーム用の低解像度ドット絵です。このロボットのデザイン・配色・装備を忠実に維持したまま、アニメの公式設定資料のようなメカニカルデザイン画として清書してください。細く均一なクリーンな線画、フラット寄りの淡い彩色、陰影は控えめに1段階のみ、ディテールは精密に、直立に近い自然な立ちポーズ、向きは添付と同じ。全身が頭からつま先まで完全に収まること。背景は一切塗らず、ロボットの輪郭の外側はすべて完全透明にした透過PNGで出力。文字・署名・ロゴ・寸法線・地面の影は入れない。キャンバスは縦長1024x1536。

- スタイルリファレンス: `tmp-unit-images/style-samples/style-C-mechdesign-FA-78-1.png`
  (量産時はこれを2枚目の参照として添付し「この画風・タッチに合わせる」と付記して画風ドリフトを抑える)
- 参照画像は旧GIFを4倍ニアレスト拡大したPNGを渡す(そのままだと小さすぎて細部を誤読する)

## 成果物仕様(暫定 — フェーズ0で確定)

- 形式: 透過PNG、キャンバス 512×512(表示は最大150px程度なので余裕十分)
- 構図: 全身、左向き(現行踏襲)、足元まで含む、キャンバス内で高さ基準の統一スケール
- ファイル名: `<型番>.png`(例 `MS-06F.png`)。DB migration で `units.image` を一括更新。

## フェーズ

### フェーズ0: スタイル決定
- スタイル仕様案を2〜3本作成(例: 現行踏襲の高精細セル塗り / スパロボ風 / 設定画風)
- 代表機1機(フルアーマーガンダム等)で各案を実生成し、並べて提示
- **採否はユーザーが現物を見て決める**(こちらで合格判定しない)
- 出口条件: スタイル仕様書1本 + スタイルリファレンス画像(以後の全生成に添付)

### フェーズ1: パイロット10機
- 有名機/マイナー機/MA/戦艦/戦車を混ぜた10機で歩留まり測定
- 測るもの: デザイン崩れ率、透過精度、1枚あたり所要時間、拒否発生率
- シート方式(1生成に4機まとめ→分割)もここで試す(地形背景で実績あり)
- 出口条件: ユーザー検収パス + 量産スループットの見積もり確定

### フェーズ2: 量産(既存585枚)
- DB→マニフェストCSV(unitId, 型番, 現画像, 状態)を生成し進捗管理
- 生成物は `tmp-unit-images/raw/` に unitId 単位で保存(検収前は public に入れない)
- 現実的ペース: 1日50〜100枚、**1〜2週間の常駐作業**。レート制限に当たったら翌日継続。

### フェーズ2b(並行): 欠落325件の設定画収集
- agy に発注: 機体名+型番のリストを渡し、設定画URLの収集とダウンロード
- 収集分を `tmp-unit-images/refs/` に保存 → フェーズ2のキューに合流

### フェーズ3: 後処理と検収
- スクリプト一括処理: 透過チェック → トリム → 512×512統一キャンバス → PNG最適化
- **新旧比較コンタクトシートHTML** を作成し一覧レビュー(ユーザー検収)
- NG指定分は再生成キューへ戻す

### フェーズ4: 組み込み
- `frontend/public/images/units/` を新PNGに差し替え、旧GIFを削除
- migration で `units.image` を `.png` 名に更新
- 将来的に R2 配信へ移す場合は `VITE_UNIT_IMAGE_BASE` を設定(既存機構)

## リスク

- ChatGPT のスタイルドリフト(枚数が進むと画風が揺れる)→ スタイルリファレンス画像を毎回添付、定期的に初期生成分と比較
- 参照画像が低解像度すぎて細部を誤解 → 崩れ率が高ければ該当機だけ設定画収集(agy)に回す
- レート制限/生成拒否 → マニフェストで状態管理し、いつでも中断・再開可能にする
- フェーズごとにコミット(main直接運用のため溜めない)
