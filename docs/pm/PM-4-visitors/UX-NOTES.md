# 見学者システム・見学者ノート UX-NOTES

本ドキュメントは、見学者システム（他人の基地・博物館閲覧機能）および見学者ノート（ゲストブック）の仕様策定に関する画面構成、データ設計素案、および主要な論点を整理したものです。

## 1. 画面構成とルーティング

### 他人の基地・博物館見学ビュー
既存の `/museum` は現在「本人専用」として実装されているため、他プレイヤーの情報を表示するためには拡張が必要です。

**案1: 既存ルートのパラメータ拡張（推奨）**
- ルーティング: `/museum/:userId`
- メリット: 既存の `Museum.tsx` コンポーネントを再利用し、`userId` パラメータの有無で「編集モード（自分）」と「閲覧モード（他人）」を切り替えられる。UIの一貫性が保ちやすい。
- UXの工夫:
  - 画面上部に常に「他人の基地を見学中」とわかるStickyバナーを配置する。
  - 「展示を編集」「コメントを保存」等の操作ボタンは条件付きレンダリングで非表示にする。

**案2: 完全別ページの作成**
- ルーティング: `/visitor/:userId`
- メリット: 編集ロジックと閲覧ロジックが完全に分離されるため、コンポーネントが肥大化しない。
- デメリット: デザイン修正時の二重管理が発生する。

### 導線
- **プロフィール画面 / ランキング画面**: 他プレイヤーの名前をタップした際に出るプロフィールモーダル等に「基地を見学する」ボタンを設置。
- **戦闘履歴（リプレイ）**: 対戦相手の基地へ飛べるリンクを配置。

## 2. データ設計素案

### 新規テーブル: `Guestbook` (見学者ノート)
他プレイヤーの基地に残すコメントを管理するためのテーブル設計素案です。

| カラム名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| `id` | String (UUID) | PK | ノートのユニークID |
| `targetUserId` | String (UUID) | FK, Index | 書き込まれた基地のオーナーID |
| `authorUserId` | String (UUID) | FK | 書き込んだユーザーのID |
| `content` | String (Text) | Max 140 char | コメント本文 |
| `createdAt` | DateTime | Default Now | 投稿日時 |
| `isDeleted` | Boolean | Default False| 論理削除フラグ（館長による削除） |

### 必要なAPIエンドポイント拡張
1. **`GET /api/museum/public/:userId`**
   - 目的: 他人の博物館展示情報、図鑑進捗サマリの取得。
   - 権限: 認証済みユーザーであれば誰でもRead可能。
2. **`GET /api/base/public/:userId`**
   - 目的: 他人の基地の基本情報（基地名、地形、館長名、博物館の建設状況）の取得。
3. **`GET /api/guestbook/:targetUserId`**
   - 目的: 特定の基地の見学者ノート一覧取得（ページネーション対応）。
4. **`POST /api/guestbook/:targetUserId`**
   - 目的: 見学者ノートへの新規書き込み。
5. **`DELETE /api/guestbook/:noteId`**
   - 目的: 投稿の削除。
   - 権限: `targetUserId` が自分自身である場合（館長権限）、または `authorUserId` が自分自身である場合のみ許可。

## 3. 論点リストとUX判断

実装にあたり、PM/開発チームで合意しておくべき論点です。

### 1. 荒らし対策（スパム・誹謗中傷対策）
他プレイヤーが自由にテキストを入力できる場であるため、対策が必須です。
- **文字数制限**: 短文の交流を促すため、最大 **140文字** に制限する（モックに反映済み）。
- **連投制限**: 同一ユーザーから同一基地への投稿は「1時間に1回まで」等のレートリミットをAPI層に設ける。
- **NGワードフィルタリング**: 本番運用に向けて、不適切ワードを弾くミドルウェアの導入を検討。
- **自衛手段（館長削除）**: 基地主（館長）は、自分のノートに書かれた投稿を自由に削除できるUIを提供する（モックに反映済み）。

### 2. 非公開設定の要否
- **論点**: 自分の基地やノートを他人に見られたくないプレイヤーへの配慮が必要か？
- **提案**: 第一フェーズでは「全員公開」で実装。交流を促進するため、デフォルトで公開とする。クレームが多い場合のみ、後続フェーズで「見学拒否」トグルを追加する。

### 3. 見学の「足あと（訪問通知）」の要否
- **論点**: 誰が自分の基地を見に来たか、履歴を残すか？
- **提案**: データベースの肥大化と、気軽な訪問の妨げ（見に行くとバレる）になるため、**明示的な足あとは実装しない**。訪問を伝えたいユーザーは「見学者ノート」に書き込むことで足あととする運用にする。

### 4. 匿名投稿の可否
- **論点**: ゲストブックに匿名で書き込めるようにするか？
- **提案**: トラブルの原因になりやすいため、**匿名投稿は不可**とする。投稿者のユーザーIDとプレイヤー名は必ず表示され、プロフィールへのリンクを持たせる。

### 5. 未建設時のフォールバック
- 訪問先ユーザーが「博物館」施設を未建設の場合の扱い。
- **提案**: 「現在建設中です」というプレースホルダー画面を表示し、見学者ノートへの書き込みも不可とする（または、ノート機能だけは基地本体の機能として先行解放するかも要検討。今回は「未建設時はノートも不可」の想定でモックを作成）。
