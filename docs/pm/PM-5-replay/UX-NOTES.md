# UX-NOTES: 防衛戦連携・リプレイ画面の設計素案

## 1. 画面構成
### リプレイ画面の表示方法
既存の `BattleAnimation.tsx` はオーバーレイ（モーダル的）として実装されていますが、リプレイの場合はURLを共有できると便利であるため、**専用ページ（例: `/replay/:battleLogId`）** としてのルーティングを推奨します。ただし、実装コストや没入感を優先し、現状のままフルスクリーンモーダルとして被せるアプローチでも問題ありません。基地や履歴一覧から「リプレイを見る」を押下した際に、`battleData` state にログデータをセットして `BattleAnimation` コンポーネントをマウントする方式が最もスムーズです。

### 既存の Log.tsx との統合方針
現状、`Log.tsx` は自分宛ての全防衛履歴をテキストベースで一覧表示しています。ここへ「リプレイを見る」ボタンを追加し、`events_json`（リプレイ用データ）が存在するログのみ再生可能にする統合が自然です。
基地画面 (`Base.tsx`) のサマリからは、複数件ある場合は Log.tsx へのリンクを、1件のみの場合は直接リプレイを再生（またはLog.tsxを開いて該当行をハイライト）する導線とします。

## 2. データ設計
### 既存API (`GET /api/defense/:id/logs`) と `battle_logs` でまかなえる範囲
現在、他人の個別戦闘（作戦）を観戦する用途として、`defense_battle_id` に紐づく直近5件の `battle_logs` を取得するAPIが実装済みです（`backend/src/routes/defense.ts`）。
また、`battle_logs` テーブルには `events_json` と `meta_json` が保存されており、これをフロントエンドに流し込むことでリプレイ再生自体は現在でも完全に機能します。

### 追加で必要な API
**基地サマリ用の「直近24hの自分宛襲撃集計」API**:
現在の `Base.tsx` の初期ロード時に呼ばれる `GET /api/base` のレスポンスに、以下の情報を追加する必要があります。
- 過去24時間以内に、自分が防衛側となっている作戦に対する `battle_logs` の件数。
- そのうちの勝利数・敗北数。
- 1件のみの場合は、そのログの `events_json`（またはログID）。

また、`Log.tsx` の履歴取得API (`GET /api/battle/logs`) でも `events_json` を取得してリプレイ可能かどうかの判定を含める拡張が必要です。

## 3. 砲台の迎撃効果の配線について
PM-1で保留された「砲台による開幕迎撃射撃」ですが、**本スレッド(PM-5)での配線を推奨します**。
理由として、防衛戦とリプレイを視覚的に楽しむ上で、「自分が設置した施設（砲台）が実際に機能している」ことをリプレイで確認できることは、ユーザーの基地強化へのモチベーションに直結するためです。
実装方針としては、`simulateBattleRound` または `simulateTeamBattle` の直前に、基地情報（砲台レベル）を参照して防衛側に先制ダメージを与えるプレターン（Turn 0）イベントを生成し、`events` 配列の先頭に追加する形が望ましいと考えます。

## 4. 論点リスト
- **リプレイの公開範囲**:
  - デフォルトでは「全員（誰でも他人の戦闘を観戦可能）」にすべきです。プレイヤー間のメタゲーム（他プレイヤーの防衛編成の研究など）を促進するためです。将来的に「非公開設定」を追加する余地は残します。
- **データ保持期間**:
  - `events_json` はデータ量が大きくなるため、永続保存は推奨しません。例えば「過去30日分」または「直近20件」といったローテーション（古いものからNULLクリアまたはレコード削除）をバッチやアクセス時に行う仕組みが必要です。
- **events_json が無い古いログの扱い**:
  - 再生ボタンを「非活性（disabled）」にし、「テキストログのみ」または「リプレイ期限切れ」と表示するUI対応が必要です（モックに反映済み）。
- **シェア機能（URL共有）**:
  - 優れた防衛戦を他のプレイヤーに共有できるよう、リプレイ画面へのディープリンク（`/replay/:id`）を提供するかどうかが追加の検討事項です。
